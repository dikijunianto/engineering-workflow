# DevQuest v1 Implementation Plan

> Execute in this session with Superpowers execution and adapter delegation; the user has authorized implementation and push.

**Goal:** Build a runnable local DevQuest with durable approval gates, multi-repository task execution, interactive runtime turns, review, and explicit GitHub PR publication.

**Architecture:** A single loopback Node server serves the dashboard and typed JSON actions. SQLite records normalized entities, while immutable artifact versions and concise checkpoints live on disk. Integration ports isolate CLI and network side effects.

**Tech Stack:** Node.js 24, built-in SQLite/HTTP/test runner, plain browser JavaScript and CSS; optional document parsers for PDF/DOCX.

**Spec:** ../specs/2026-09-06-devquest-v1-design.md

## Global constraints

- Local-only; do not deploy this application.
- Explicit TRD and plan approvals, Jira publication, and PR creation.
- One Quest × one repository = one worktree + branch + PR, targeting development.
- Sequential within a RepositoryWork, parallel across eligible repositories.
- Preserve progress on interruption; no persistent raw terminal or chat history.
- Browser actions cannot select executable commands; credentials stay outside SQLite/artifacts.
- Work in the current project as requested, on feat/devquest-v1; push this branch without force.

## Decisions

- Retain the current project folder and use a feature branch, following the user's folder preference.
- Runtime provider authentication and existing Jira skill setup are user-machine prerequisites; automated tests never spend model credits or publish real Jira/PR records.
- Live conversation is turn based; application checkpoints enable logical resume with vendor session persistence disabled by default. This preserves the specified retention boundary.
